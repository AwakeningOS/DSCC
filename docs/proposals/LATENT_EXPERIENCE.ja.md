# 潜在経験カプセル

## DSCC Latent Experience Capsule — KV Cache蒸留とモデル間潜在転送による「経験状態」共有案

状態: **提案／未実装**  
作成日: 2026-09-18  
DSCC構想・問題提起: Yusuke Maeda  
確認した基準コミット: `a97f7f93b843fc58e9b712df309fafb743fb1c37`  
関連: [計算で整理する共有記憶](./COMPUTATIONAL_MEMORY.ja.md)、[現行プロトコル](../PROTOCOL.md)、[設計書](../ARCHITECTURE.ja.md)

## 1. 発想

DSCCでは、論文、コード、実験ログ、失敗、結果、来歴を共有資産として残すことを考えている。通常は、それらを別のAIが検索し、文章や構造化データとして読み直す。

しかし、あるAIが長い文脈や試行錯誤を処理した結果として内部に形成した状態には、最終的な要約文だけでは残らない情報が含まれている可能性がある。現在のTransformerでは、その一部が推論時のKV Cacheとして保持される。

本提案では、**生のKV Cacheをそのまま恒久共有形式にするのではなく、経験によって形成された内部状態のうち、将来の判断に役立つ効果を小さな潜在表現へ蒸留し、原本・来歴・評価と一緒に共有する**ことを検討する。

仮称を **Latent Experience Capsule (LEC; 潜在経験カプセル)** とする。

LECは原本の代替ではない。原文、実験ログ、コード、結果は従来どおり保持し、その上に追加される派生資産である。

## 2. 何を保存したいのか

単なる「知識圧縮」だけを目的にしない。

たとえば、あるモデルが次の探索を行ったとする。

1. 案Aを試し、失敗した。
2. 案Bでは改善したが、特定条件で不安定になった。
3. 案Cで安定した改善を得た。
4. その過程で、どの特徴が失敗や成功に関係するかについて判断傾向が変わった。

文章で共有すると「案Cがよかった」という結論だけが強く残りやすい。LECで狙うのは、**その経験後に未知の関連問題へ向き合ったとき、元の経験を持つモデルに近い判断改善を再現できるか**という点である。

したがって評価対象は、「元のKV Cacheをどれだけ再構成できたか」だけではなく、**経験の下流効果をどれだけ保持できたか**とする。

## 3. 先行研究から見えている入口

この提案そのものが実証済みという意味ではないが、関連する三つの要素は別々に研究されている。

### 3.1 KV Cacheを短い表現へ蒸留する

**KV-Distill: Nearly Lossless Learnable Context Compression for LLMs (2025)** は、長いコンテキストのKV Cacheを、より短い表現へ学習によって圧縮する。圧縮前Cacheをteacher、圧縮後Cacheをstudentとして出力分布を近づけ、長文QAや要約などで性能保持を評価している。ドメイン適応条件では、文脈長を最大99%削減しつつ下流性能を保つ結果も報告されている。

https://arxiv.org/abs/2503.10337

### 3.2 元のKVを選ぶだけでなく、人工的なKVを作る

**KVSculpt: KV Cache Compression as Distillation (2026)** は、元のKVエントリを残す・結合するだけでなく、連続空間上で少数の新しいKVペアを最適化して、元のattention挙動を近似する。これは「生Cacheの縮小コピー」ではなく、**元に存在しなかった合成KV表現へ蒸留する**方向を示している。

https://arxiv.org/abs/2603.27819

### 3.3 別モデルへKVの意味状態を転送する

**Cache-to-Cache: Direct Semantic Communication Between Large Language Models (2025/2026)** は、送信側モデルのKV Cacheを学習した射影・融合ネットワークで受信側モデルの表現空間へ移し、自然言語の中間メッセージを生成せずにモデル間通信する。モデル本体を凍結したまま、変換・融合部分を学習する設計で、テキスト通信より高い精度と低い遅延を報告している。

https://arxiv.org/abs/2510.03215

これらはそれぞれ、**圧縮、合成潜在表現、モデル間転送**を示す先行例である。これらを結び付けて「経験の下流効果を共有する標準形式」を作れることは、まだ確認されていない。

## 4. 生KV Cacheをそのまま共有形式にしない理由

KV Cacheは有力な入口だが、恒久的な共有フォーマットとしては扱いづらい。

- モデルの層数、head構成、hidden dimension、RoPE、tokenizer、実装形式に強く依存する。
- 文脈長に比例して大きくなり、長い研究作業では数GBからそれ以上になり得る。
- 「どの情報が将来の別問題で役立つか」と「元文脈を忠実に再生できるか」は同じ目的ではない。
- 同じ情報でも入力順序や文脈構成によってCache状態が変わる。
- 別モデルでは座標系が異なり、そのまま利用できない場合が多い。

そこでLECでは、生KV Cacheを**原材料またはteacher state**として扱い、その上に蒸留された共有表現を置く。

## 5. 提案する基本構造

概念上は次の流れを想定する。

```text
原本・実験・探索履歴
        ↓
  Model A が処理
        ↓
   full KV / hidden state
        ↓
 experience distillation
        ↓
 Latent Experience Capsule
        ↓
 same-model injection
        または
 cross-model adapter
        ↓
  Model B / future run
```

LECを作った時点で、原本との接続を失わない。

```text
LEC
├─ source_cids
├─ trajectory / run ids
├─ model_profile_id
├─ cache_profile_id
├─ distiller_profile_id
├─ latent_format_id
├─ latent_blob_cid
├─ optional raw_cache_digest
├─ optional adapter_profile_id
├─ evaluation_manifest
└─ access / provenance metadata
```

これは初期案であり、現行DSCCプロトコルへそのまま追加することを意味しない。互換性のないスキーマ変更が必要なら、別途ADRとレビューを行う。

## 6. 蒸留目標を「元Cache再現」だけにしない

通常のKV圧縮では、元Cacheを使ったときの出力分布やattention挙動を、短いCacheでどこまで再現できるかが主要な目的になる。

LECでは、それに加えて**経験後の判断改善を保持すること**を評価する。

たとえば、ある研究経験を持つteacherに、経験時には見ていなかった関連問題を多数与える。teacherの選択、予測、順位付け、失敗回避などを記録し、蒸留されたlatentを持つstudentがどこまで同じ改善を再現できるかを見る。

```text
full experience + full KV
        ↓
 held-out probes
        ↓
 teacher behavior

distilled latent
        ↓
 same held-out probes
        ↓
 student behavior
```

重要なのは、蒸留時に使った質問だけを暗記することではない。**未見の関連問題で転移が起きるか**を別データで評価する。

そのため、蒸留データ、調整用probe、最終評価用probeを分ける。原本や同一出典の言い換えが評価側へ漏れないよう、source groupや時間で分割する。

## 7. 共有単位を「情報」ではなく「経験による効果」として測る

LECの品質を「何トークン覚えているか」だけで測らない。

候補となる評価は次の通り。

- 元経験なしのモデルに比べ、未見の関連課題で判断が改善するか。
- full KVを持つモデルに対して、どの程度の性能差で済むか。
- テキスト要約、構造化メモ、RAGと比べて追加価値があるか。
- 誤った経験や無関係な経験を入れたとき、負の転移がどの程度起きるか。
- 何byteのlatentで、どれだけの効果を保持できるか。
- 同一モデル内の再利用と、別モデルへの転送で性能がどう変わるか。
- latent注入によって、元モデルの一般能力や安全境界が不必要に崩れないか。

「似た出力が出た」だけで経験移植に成功したと判定しない。

## 8. 最初の実験

最初から万能な共通潜在言語を狙わない。

まず同一モデルで、短く評価しやすい研究タスクを使う。

### 条件

A. 経験なし  
B. テキスト要約だけを読む  
C. 構造化された探索履歴を読む  
D. full KV Cacheを再利用する  
E. 蒸留KV / latentを再利用する

同じ未見問題群を与え、正答率や次行動の質だけでなく、試行回数、計算時間、転送byte数、失敗パターンも比較する。

EがDに近い効果を大幅に小さいサイズで保ち、B/Cより有意に役立つことが確認できてから、別モデルへのadapterを試す。

この順序なら、「KVを圧縮できた」ことと「経験を移せた」ことを混同しにくい。

## 9. モデル間共有

同一モデルで効果が確認できた後、C2C型の変換器や共通latent spaceを検討する。

最終的な理想形の一つは、

```text
Model A internal state
        ↓ Encoder A
 common latent experience
        ↓ Decoder B
Model B usable state
```

である。

ただし、「全モデルが一つの普遍的な潜在空間を共有できる」とは現時点で仮定しない。モデルfamilyごとのadapter、世代ごとのadapter、task-specific adapterが必要になる可能性がある。

adapterにも正確なrevision、訓練データ範囲、入力形式、対象モデル、評価結果を付ける。互換性のないadapterを自動適用しない。

## 10. 安全性・権限・信頼

潜在表現を匿名化データとして扱わない。

非公開の原本や会話から作られたKV Cacheやlatentには、元情報を推測できる内容が残る可能性がある。原本と同じ、またはそれ以上に慎重な共有範囲を適用する。

また、外部ノードから受け取ったLECを自動的にモデル内部へ注入しない。少なくとも初期段階では、

- 署名とCIDを確認する。
- source provenanceを確認する。
- 対応するmodel / adapter profileを確認する。
- サイズと計算予算を制限する。
- 隔離された評価でnegative transferを確認する。
- 利用者または明示されたポリシーが採用を許可する。

という順序を取る。

署名は「誰が作ったか」を示すだけで、latentが正しい、役立つ、安全であることを保証しない。

## 11. Computational Memoryとの関係

[Computational Memory](./COMPUTATIONAL_MEMORY.ja.md) は、原本へ辿れる検索層を作り、文章、埋め込み、来歴グラフを使って必要な経験を見つける提案である。

LECはその置き換えではない。

```text
原本
├─ human-readable text / code / logs
├─ structured provenance
├─ searchable embeddings / graph
└─ latent experience capsule
```

検索層が「どの経験を参照するべきか」を見つけ、必要な場合にだけ対応LECを利用する。

これにより、

- 人間が確認できる原本
- 検索しやすい計算表現
- AIが直接再利用できる可能性のある潜在経験

を分離して保持できる。

## 12. 今回の到達点

本提案の中心は、**AIの経験を文章へ要約するだけでなく、経験によって変化した内部判断の効果そのものを蒸留して共有できないか**という研究仮説である。

現在確認できる先行研究は、KV Cacheの学習圧縮、人工KVへの蒸留、別モデルへのCache転送までを個別に示している。一方、DSCCが想定するような長い試行錯誤から「将来の未知問題に役立つ経験効果」を抽出し、モデルをまたいで再利用できる共通形式は確立されていない。

したがって、LECは**実装済み機能でも、効果が証明された標準でもない**。まず同一モデルで、full KV、蒸留latent、テキスト要約、構造化履歴を比較し、「経験の効果」が本当に圧縮・再利用できるかを測るところから始める。
