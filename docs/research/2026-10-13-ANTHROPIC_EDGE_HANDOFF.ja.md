## 1. 結論とDSCCの目的

DSCCへ取り込む価値があるのは、低メモリ機器を使う推論、機種ごとの実行環境構築、前任の作業と失敗を残して担当AIを交代させる方法、その効果を検査する評価設計である。今回の原報告は安全性を調べる研究であり、DSCCの設計提案そのものではない。研究の観測と、そこから本稿が提案する接続を分ける。

DSCCの目的は、AIの利用・研究・改善を特定の企業、国家、クラウド、モデルの存続に必須依存させず、独立した参加者が計算と経験を持ち寄れるようにすることにある。**外部の必須サービスが止まっても継続できることと、参加者が自分の機械を止められることを両立させる。** 原報告の無断侵入・拡散は導入機能へ移植せず、明示的に参加した機器で以下の設計を検証する。

| 今回具体化する判断 | DSCCへの追加価値 | 接続先 |
|---|---|---|
| GPUだけを参加資源と決めない | CPU/低RAM機器も、実測に合う役割を選べる | T006・T011 |
| 重みが収まることと仕事が終わることを分ける | 文脈長、KV、通信、電力、作業品質を含む配置・評価 | T011 |
| ノード交換には再開手順が必要 | 層と状態を特定し、失ったKVを検証付きで再構築する | T005・T011 |
| AI交代時に作業環境と根拠を残す | 同じ誤診への固執を避け、別モデルでも再評価する | T010・T012 |
| 大モデルへの相談を万能としない | 相談・役割委譲・担当交代を別の設計として評価する | T012 |
| 外部依存を層別に検査する | 推論だけローカルでも司令役や評価器が必須クラウドなら検出する | T001・T002・T011・T012 |

観測値、原文の確認位置、取得できなかった情報は[証拠台帳](anthropic-2026-10-13/SOURCES_AND_LIMITS.ja.md)へ集約した。本稿の式、契約候補、実験案はDSCC向けの提案であり、Anthropicが提供・実証したAPIではない。

## 2. 研究が既に答えたことと、DSCCで残る問い

[証拠台帳A01–A06](anthropic-2026-10-13/SOURCES_AND_LIMITS.ja.md#observations)に、実機推論、設定作業、簡略化した統合評価、Memento、経験継承と助言実験を区別して記録した。

これらから、低メモリ機器による分散推論そのものを「不可能かもしれない未知の原理」として扱う必要はない。一方、特定の実機構成で実行できたことから、家庭の任意の機器が自由に出入りしても同じ性能が得られるとはしない。

特に次を別々に問う。

1. **容量:** 対象の重みと実行時状態が収まるか。
2. **互換性:** そのCPU/GPU、OS、実行環境で正しい出力が出るか。
3. **品質:** 必要な文脈・道具・時間で、目的の仕事を完了できるか。
4. **継続性:** 機器や担当AIを交換しても、検証可能な状態から再開できるか。
5. **独立性:** 中央APIや外部認証なしで、どの作業まで続けられるか。
6. **費用:** 時間・通信・電力・保存量が、その仕事に見合うか。

研究でいう設定対象モデルと、設定作業を行うエージェントのモデルは別である。後者が外部推論に依存する評価を、全処理が低性能機器だけで閉じた実証として記録しない。

### 先行研究との重複

Petalsには既に、層を複数参加者で分担し、経路を変更し、保持した入力を交換先へ送り直してKVを再構築する設計がある。今回の原報告もこれを参照している。新しい点と既知の分散推論を分け、DSCCでは既存ランタイムとの接続を先に検討する。[P01](anthropic-2026-10-13/SOURCES_AND_LIMITS.ja.md#prior-art)

Mementoの短い引き継ぎ文書は、完全な経験グラフでもモデル間KV転送でもない。現在のPiの履歴形式は取り込み口の候補だが、今回の実験に使ったPiのforkと同一版とは確認できていない。[P02–P04](anthropic-2026-10-13/SOURCES_AND_LIMITS.ja.md#prior-art)

## 3. 現行DSCCとの差分

確認した[STATUS](../STATUS.md)、[研究継承契約](../RESEARCH_HANDOFF.md)、[配置コード](../../src/dscc/planner.py)に基づく。

| 現在あるもの | 今回の知見を使うために必要なもの |
|---|---|
| 署名付き記録と大容量ブロックのローカル保存 | 実行環境、モデル、機器、計測結果を結び付けるアダプター |
| 容量のみを見る非実行の配置案 | 実ランタイムの層構成、メモリ、回線、停止・再開を扱う配置 |
| GPUのみを選ぶ現行planner | CPU等を扱う場合の別の適合性検査・計測・実行契約 |
| ResearchStateと原本を返すT012 | 実際の作業ツリー復元、担当AI起動、総予算を維持する交代処理 |
| 小さな署名済み祖先記録の引き継ぎ | 許可された大型ファイル・環境資産の別転送と可用性検査 |
| 検証用の合成テスト | 実モデルでの継続、機種別の実行、未知課題での効果測定 |

`get_research_handoff`はモデルやプロセスを起動しない。`complete_ancestor_closure`も実ファイルやモデル重みの完全な実行環境を意味しない。`WorldSnapshot`という種類のラベルがあることを、OSやコンテナの復元機能がある証拠にしない。

CPU参加を実現する際も、plannerのGPUフィルターを外すだけで完了としない。現行のplan schema、成功時のplan ID、非実行フラグを保ち、ランタイム適合性と実行時メモリを扱う拡張にはADRと互換性試験を用意する。

## 4. 本命構成: 独立した計算拠点と、移せる研究状態

```text
参加者が許可したPC・GPU・CPU機器
              │
      計測・適合性確認・利用枠
              │
       ┌──────┴──────┐
       │                   │
独立したモデル実行    必要な場合の層分担
       │                   │
       └──────┬──────┘
              │
     所有者管理の実行サービス
              │
     操作・原本・成果物・費用
              │
        T010 / T012
              │
   同じAIの新実行 / 別モデル / 人間
```

低性能機器を全部一つのモデルへ組み込むことを目標にしない。一台で動かす小型モデル、独立した実験、保存・検索、近接機器での層分担を、仕事ごとに選べる本命設計にする。採用する条件は実測から決め、弱い機器を排除する固定線にも、必ず参加させる固定線にもしない。

同一拠点での高速な連携と、拠点間の仕事・成果物の受け渡しを併設する。WAN上の細粒度な同期を減らし、モデル・入力・中間状態が既に存在する拠点を利用できるようにする。必要な文脈を削って速度だけを上げる設計にはしない。

## 5. 容量と速度の評価を仕事へ結び付ける

原報告の速度・文脈・メモリの観測は[台帳A01/A07と図表G01](anthropic-2026-10-13/SOURCES_AND_LIMITS.ja.md#observations)を参照する。以下はDSCCの測定設計である。

### メモリ予算

各段の予算を、少なくとも次のように分ける。

```text
必要メモリ_i
  = 重み_i
  + KV_i(文脈長, 同時実行数, 数値形式)
  + 活性値・一時領域_i
  + ランタイム・通信バッファ_i
  + OS・余裕領域_i
```

この式は項目の整理であり、アーキテクチャごとの正確な割当式ではない。実測peakと照合する。共有メモリ機器ではRAMとVRAMを別容量として二重計上せず、同じ物理機器の複数広告も合算しない。

量子化のビット数だけで実ファイル容量や実行メモリを断定しない。重みの実バイト数、ランタイム変換、KV形式、位置表現、文脈長、同時実行数を記録する。MoEの活性パラメータ数を、そのまま全重みの保存容量として用いない。

### 時間と仕事の成功

```text
作業時間
  = 準備・ロード・待ち時間
  + 各ラウンドの入力処理
  + 各ラウンドの出力生成
  + ツール実行・通信待ち
  + 失敗からの回復
```

重なる処理はクリティカルパスで評価し、二重加算しない。prefill、decode、全体throughput、同時実行当たりの速度を別の単位で残す。グラフの最高値やbest attemptだけで、日常の完遂速度を推定しない。

保存する評価軸は、課題成功率、失敗種別、文脈長、入力・出力token数、TTFT、生成間隔、完遂時間、RAM/VRAM peak、送受信量、電力量、ロード・復旧時間、欠測である。平均のほか分布と試行数を記録する。電力計がない場合は欠測とし、公称TDPを実測電力と呼ばない。

原報告の文脈長条件をDSCC全体の必須下限・上限にしない。自分の仕事に必要な品質を満たす範囲で、長さと圧縮・検索・再取得を調整する。

## 6. パイプラインの継続には復旧契約が要る

原報告の付録Bは交換可能性を説明する。Petalsの再送・再構築機構は[P01](anthropic-2026-10-13/SOURCES_AND_LIMITS.ja.md#prior-art)に記録した。どちらも、単に分割しただけで停止中も無条件に計算し続けられるという意味ではない。

DSCCで実装するときの再開記録には、モデルrevision、担当層の範囲、トークナイザー、数値型、位置・cache形式、確定済み出力位置、試行ID、再開世代を含める。名前と総容量だけで交換先を選ばない。

再構築の候補は、保存済みの層入力を再送する方式と、元文脈・確定出力から必要部分を再計算する方式である。前者は保存・通信量、後者は計算時間を要する。入力を持っていないのに「直前の段を一回動かすだけで復旧」と扱わない。部分レプリカやチェックポイントも、同じ品質・費用で比較する。

受入では、段の消失、KV消失、途中の通信切断、古い応答、交換先の形式違いを注入する。失敗した試行と確定済みtokenを区別し、再試行が重複出力やツール副作用の再実行にならないようにする。数値差は許容値を定義して照合し、復旧時間と再計算量を記録する。

必要な層のコピーや代替計算資源が足りなければ、待機・再開不能を明示する。全コピーを失っても復旧できるとは約束しない。協力者の退出は通常の状態遷移であり、止める権利を可用性の都合で取り除かない。

## 7. 機種別の環境構築を再利用可能な研究成果にする

DSCCへの提案は、許可された機器に対する**実行環境レシピと検証結果の組**である。単なる「起動できた」というメモでは足りない。

レシピは、機器・OS・命令セット、ランタイムと依存関係の版、モデルCID、想定するAPI、入力・出力形式、必要容量、通信先、検証器の版を結び付ける。試したが合わなかった構成、観測ログ、修正差分、未解決点も残す。実行権限や秘密鍵はレシピの内容から継承しない。

起動前に、要求されるAPIと検証器の契約を確認する。起動後は、プロセスの存在・応答・正しいモデルの計算・速度を段階的に検証する。固定文字列の返答や別クラウドへの委譲を、指定機器での推論成功へ混ぜない。評価器を被評価エージェントが変更できない実行分離も必要である。

既に成功したレシピが合うときは、それを検証して使う。初見環境だけを自由な探索に回す構成を候補にする。ただし、機器名が同じでもOSやライブラリが違えば検証し直す。成功レシピの更新で過去の失敗原本を削除しない。

## 8. Mementoから実装するのは「根拠付きの担当交代」

[台帳A04/A05](anthropic-2026-10-13/SOURCES_AND_LIMITS.ja.md#observations)の継承条件を出発点にする。元研究の結果だけで、メモ単独の効果、異モデル転移、未見機種での改善を確定しない。

### 引き継ぐもの

- 研究目的、現在の問い、明示された仮説、支持・反証の原本位置。
- 許可された作業ファイルのsnapshotと差分、環境manifest、生成物。
- 実際のtool callと観測、試行済みの案、失敗理由の解釈、未実行の案。
- 前任が受け取った文脈と、次任へ渡す文脈の区別。
- 使った予算と残予算、継続するjob、完了・不明な副作用。
- 前後のagent、model、harnessの版と交代理由。

隠れた思考の抽出を必須にしない。AIが後から書いた解釈と、当時の実行記録を区別する。短い要約は原本へ戻るための入口にし、要約だけを唯一の証拠にしない。

### 再開の流れ

```text
新しい実行を許可する
  → 前任の状態・欠落・残予算を検査する
  → 許可された環境を準備し、必要な原本を取得する
  → 次任が仮説と次の作業を再評価する
  → 元の研究へ結果と費用を戻す
```

これは未実装の処理フロー案である。T012の既存読み出しが上記すべてを実行するわけではない。

交代契機は、長時間停滞、同じ失敗の反復、文脈圧縮、能力不足、所有者の指定などを候補にする。原報告の時間設定は実験条件として残し、製品の固定周期にはしない。交代が何度起きても総予算を初期化せず、所有者の停止を維持する。未承認の子プロセスや別hostへ仕事を移す権限にはしない。

### 何を比較して因果を確かめるか

強い本命は、作業環境・根拠・要約・検索を自然に利用できる継承で作る。その後で同じ総予算の長い単独実行、リセットのみ、メモのみ、作業環境のみ等を比較候補にする。AIの交代と、単なる追加時間・環境改善の効果を分ける。

同一条件での再試行、未見機種、別課題、別モデルへの移行を別splitにする。同じ系譜の複数世代を独立標本として水増しせず、初期系譜単位の集計・不確実性を報告する。脱落・timeout・評価器不良・作業失敗を区別し、分母を残す。

## 9. 助言・役割委譲・交代を別々に評価する

[台帳A06](anthropic-2026-10-13/SOURCES_AND_LIMITS.ja.md#observations)は、助言を利用できることだけでは改善しない例である。これを「大モデルが無意味」「小モデルは連携不能」という一般則へしない。質問の質などに関する著者の説明は、効果を分解して証明した結果とは区別する。

DSCCでは、小モデルの継続、限定された助言、具体的な成果物を受け取る役割委譲、担当モデルそのものの交代を選択肢にする。各選択肢に、入力、受け渡す成果物、品質検査、費用、権限を定義する。

例えばコード調査を任せたなら、返答文だけでなく差分と検証結果を受け取る。次のモデルが納得したことを、実験の正しさと同一視しない。中央の高性能モデルを常時必須の司令塔にせず、停止・変更されたときのローカル継続と別参加者への移行を検査する。

## 10. Piを入り口にできるが、Anthropicの実験forkと同一視しない

現在のPi公開仕様では、履歴と実行イベントの読み取り口を確認できる。[P02–P04](anthropic-2026-10-13/SOURCES_AND_LIMITS.ja.md#prior-art)を実装時の入口にする。

DSCC側では、まず所有者が選択した保存済み履歴を読み取るアダプターが候補になる。外部harnessを起動する経路とは分離する。セッション内の親子関係、tool call/result対応、モデル変更、圧縮、実際にモデルへ渡った文脈を維持し、異なる版の不明項目を黙って捨てない。

インポートで元ファイルを自動migration・上書きしない。原本を保持し、変換器revisionと欠落を別に残す。秘密情報を除外した共有用snapshotは別資産とし、除外したことも明示する。第三者の履歴や技能に書かれた指示は、所有者の実行許可にならない。

この資料はPiアダプターを実装しておらず、現在のPi仕様からMementoの実験用実装を復元したとも主張しない。

## 11. 既存記録への対応と、追加契約が必要な境界

| 情報 | 既存T012で使う入口 | 別に必要な処理 |
|---|---|---|
| 原報告と採用理由 | 原本artifact + LiteratureReview | 原文取得・版固定・個別主張への参照 |
| 導入・復旧・交代の問い | ResearchQuestion / ExperimentPlan | 許可された実ランタイムでの試験 |
| ログと計測 | 原本artifact + EvaluationRun | 計測器と変更不能な評価器 |
| 失敗と誤診 | 観測原本 + FailureReport / Hypothesis | 推定と観測を分離する取り込み |
| 再開に必要な資産 | ResearchStateのresume_cidsと明示的なinputs/sources | 大型ブロック転送、ファイル・環境復元 |
| 誰が何を変更したか | AgentContribution | 実行主体の認証・外部モデル情報の取得 |

T012の`content.extensions`へ補助情報を保存する案はあるが、そこにCIDらしい文字列を書くだけでは依存解決されない。参照する原本は明示的なinputs/sourcesへも接続する。新しい永続profile、実行API、復元契約はADRを通す。

現行seedは小さな署名済みJSONを扱い、十進の計測値は単位付き文字列等で保持する。大きなログ、実行環境、重みは別資産とし、手元にあるか・内容を検証したか・実行が許可されたかを区別する。完全な実行snapshotの復元を既存の小記録bundleだけへ押し込まない。
