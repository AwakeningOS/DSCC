## 1. 本命の構成

```text
原本保管：文献・コード・設定・観測・失敗
        │
        ├── 複数の再構築可能な検索／記憶ビュー
        │                   ↓
        │            実際の提示内容の記録
        │                   ↓
        ├── 任意の過去候補 ─ 改良候補を作るAI／人間
        │                   ↓
        │              所有者が許可した実行
        │                   ↓
        ├── 評価条件 ── 試行ごとの観測・費用
        │                   ↓
        └──────── 採用／不採用／保留の根拠
                            ↓
                    次のResearchState
                            ↓
              別モデル・別参加者が検証して継続
```

改良役は、必要なら複数の過去候補、反証、コード、原本を参照する。直前の要約だけ、固定された役割数、固定された親一つに閉じない。選択的な読み出しは、全履歴を一度にコンテキストへ詰めることとは違う。

モデル、ハーネス、検索、要約、評価を別々に交換可能にする。ローカル完結経路を残し、外部の強いモデルは参加者が選ぶ追加資源とする。評価の承認はそのプロジェクトの判断であり、全ネットワークで唯一の正解や一括配備命令ではない。

## 2. 既存契約に載せる対応

| 論理的に残したいもの | 既存の保存先候補 | 必須の関連付け |
|---|---|---|
| 文献、コード、設定、実行ログ | seed Artifactの適切なkindとdata | 原本、版、出所、ライセンス、条件 |
| ハーネス構成一式 | 構成を記述するArtifact、またはAgentContribution | コード・設定・モデル・道具・環境・検索方針の原本参照 |
| 変更による改善の仮説 | Hypothesis | 候補の構成、参照した過去候補・失敗、statement/rationale |
| 改善対象の問い | ResearchQuestion / OpenQuestion | 未解決点、評価基準 |
| 比較条件 | ExperimentPlan | question_cid、比較する構成、評価器・データの版 |
| 試行結果 | EvaluationRun | plan_cid、observation source、観測と解釈の分離 |
| 失敗・中断 | FailureReport | attempted、observed、残る問い、原観測 |
| 採用・不採用・保留 | AgentContribution | description、候補と評価への入力参照、決定理由 |
| 継続地点 | ResearchState | finding_cids、open_question_cids、resume_cids、next_actions |

kindのラベルだけでは意味の妥当性を強制できない。専用の型を実装する場合は、別のADRと契約テストを作る。今回は `dscc.research/0.1` の認めるtype集合を変更しない。

`content.extensions` は名前空間付きの補助情報を保つ候補である。ただし、拡張内のCID文字列は自動で親参照にならない。依存する原本は `input_cids` / `sources` にも明示する。拡張の保存は、評価器の固定、秘密情報の隔離、予算強制、実行許可を保証しない。

## 3. 記録へ含める情報

以下はadapterの設計候補であって、そのまま受け付ける新schemaではない。

### 3.1 構成と改良候補

構成にはコード、設定、道具の実行物と依存環境、モデル・tokenizerの識別、記憶・検索方針、必要なデータを参照させる。閉じたproviderのsnapshotが不明ならnullとし、便宜的なモデル名をimmutableな重みCIDと同一視しない。

改良候補には、参照した構成群、何を変更したか、期待する効果、想定する失敗条件を残す。単一の直前候補から派生したことを強制せず、複数候補の良い部分を組み合わせられる。過去の原本を変更せず、新しい候補と比較で表す。

### 3.2 検索から提示まで

検索質問、許可された対象範囲、索引世代、encoder、順位付け、選択・圧縮方式の版を残す。候補リストと、実際にモデルへ入れた順序付きの抜粋・要約を分離する。抜粋は原本CIDとJSON Pointer等の位置情報へ戻せるようにする。長い入力では、組立方式、切詰め、tokenizer、予算も記録する。

「候補になった」「提示した」「AIが使用を申告した」「行動・成果物で参照された」は別の状態とする。観測できない使用はunknownにし、後から推測した理由を実行ログとして書き換えない。公開記録にhidden chain of thoughtを必須としない。

機密データは候補生成・グラフ展開の前に範囲を制限する。本文だけでなく候補の存在・ID・件数も漏えいし得る。現行のproject名はACLではないため、混在コレクションの安全性を宣言せず、境界が実装されるまでは別node homeを使う。

### 3.3 評価・採否・費用

評価器、採点ルール、課題集合、環境、モデル版を特定し、各試行に成功・失敗・中断・未実施・不明を区別して残す。得点ゼロと未実施を同一にしない。原ログ、計測値、解釈、採否を別にする。

費用は実行役だけでなく、提案役、批評役、検索、評価、通信を含む。単位を明示し、未知の費用をゼロで埋めない。現行canonical metadataでは小数は文字列で保存する。固定予算で比較する場合、交代・再試行・分岐を含む総量を記録し、成功した枝だけの費用を報告しない。

採否には対象構成、参照した評価、決定者、基準の版、未解決の反証を残す。別参加者が同じ証拠から異なる採否を記録してよい。評価器・解釈の変更は別の版として履歴を保つ。

## 4. 引き継ぎと実行再開を分ける

| 段階 | 確認すること | 現行実装だけで主張できるか |
|---|---|---|
| 記録の引き継ぎ | 必要な署名済み小記録と参照が有効 | 既存のbounded handoffで扱う |
| 資産の準備 | コード、重み、環境等の必要なバイト列が取得・検証済み | 小記録handoffだけでは不可 |
| 環境の再構成 | 指定環境を構築し、道具・モデルの動作を検証 | 別runtime・実機試験が必要 |
| 仕事の継続 | 実モデルが引き継いだ情報で課題を継続 | T012の実モデル実験が必要 |
| 改善の継続 | 後任が手順を改良し、未知課題でも効果を確認 | さらに品質・費用評価が必要 |

Small-recordの祖先閉包が揃っても、重みやコンテナ・作業ディレクトリが復元されたとは限らない。任意のコード文字列を読み込んだだけでimport/execしない。実行は所有者の許可した経路を使う。現行の同一OSユーザーのCLI/MCPは強い隔離ではない。

再実行の分類案:

- 純粋な計算や隔離したファイル変更: 入力・環境を確認して再計算／復元する候補。
- 補償可能な外部操作: 補償手順と、その成功確認が必要。
- 不可逆な外部操作: 履歴の巻き戻しでは取り消せない。重複実行を避ける照合・承認が必要。

不明な操作は無条件に再実行しない。Shepherdの取り消し機能を、現実の全副作用の取り消しと解釈しない。停止済みの参加者を復元処理で再参加させたり、新しい試行に前の実行許可をコピーしたりしない。

## 5. 評価データを履歴から漏らさない

最終評価の回答・観測・得点を、改良を提案するAIの探索履歴に混ぜない。要約、検索索引、候補一覧、評価コメント経由の漏えいも対象とする。出典系列と時点で調整用・最終評価用を分離する。同じ試行の子孫や言い換えを、独立した評価データとしない。

非公開評価データを親に持つResearchStateを、そのまま提案役へexportしてはいけない。現行exportは祖先の内容を含むため、public/privateの切替ラベルだけでは保護されない。公開してよい評価記録と、隔離された評価側の原本を分け、どの範囲だけ共有したかを明記する。これを自動で安全に行う機構は未実装である。

本命のモデル、役割、探索方式には必要な自由度を残す。評価中の同一条件と、製品として永久に変更できない制約は別である。評価器を改善したら新しい比較として記録する。

## 6. 現行のサイズ上限を無視しない

[seed protocol](../../PROTOCOL.md)では1記録は最大1 MiB、直接の親は32個、exportは256記録・8 MiBまでである。長期に増える全履歴を一つのResearchStateの祖先へ永久に追加する構成は、この上限と衝突する。

最初の接続試験は、境界が明らかな小さい研究エピソード単位で行う。長期の本命では、段階的に取得する原本、検索用の再構築可能なcatalog、依存manifestの扱いをT005/T007と設計する。ただし、manifestを階層化するだけでは、現行exportが辿る推移的祖先数は減らない。

省略した依存を「完全に引き継いだ」と表示しない。未取得・別途取得・完全な祖先閉包を区別する契約が必要である。上限をこっそり上げたり、未解決のCIDをextensionsに隠して検証を迂回したりしない。この容量問題は本命の歴史参照能力を捨てる理由ではなく、転送契約を別途設計する理由である。

## 8. 12項目の受入条件

**すべて提案であり、この資料追加で実行したテストではない。** 既存CIの成功とこの表の達成を混同しない。

| ID | 試験と必要な証拠 |
|---|---|
| B01 | 構成・経験から元のコード、観測、版、条件へ戻れる。欠落・改変は完全なhandoffとして返さない。 |
| B02 | 候補に出たが提示していない資料を用意し、候補取得と実際の入力が区別される。 |
| B03 | 誤った要約から原本へ戻って訂正でき、古い要約・反証・訂正の系譜も残る。 |
| B04 | 議論前後の案と参照元を保持し、同一出典や同一生成系列を独立した支持に数えない。 |
| B05 | 不採用・中断・失敗を含む全候補と費用を保ち、成功した枝だけを選んだ報告を区別する。 |
| B06 | 実際にモデルを変更して構成と原本から再開し、記録の転送と環境復元・性能を分けて測る。 |
| B07 | 比較中の評価器・データ版を検査し、候補が採点条件を書き換えて勝つ経路を実行側で防ぐ。 |
| B08 | 出典系列・時点で評価を分け、原本、要約、索引、祖先export経由で保留評価が漏れない。 |
| B09 | 品質、失敗反復、試行数、全役割のモデル・検索・通信費用を計測し、未計測をunknownにする。 |
| B10 | 選抜された学習サンプルから元の成功・失敗・生成条件・検証器・選抜理由へ戻れる。 |
| B11 | 遠隔モデル、検索、評価の各サービスを外し、ローカル代替で続く部分と停止する部分を実測する。 |
| B12 | 再開・交代・分岐で停止や総予算を解除しない。不可逆操作の重複と上限超過を検出する。 |

B01–B05等には記録レベルの試験を作れるが、それだけでB06以降の実行・品質・秘密情報保護を実証したとはしない。上限付近の閉包、未取得large block、同一モデルの別名、評価器すり替え、候補IDの漏えいも具体的な境界例として扱う。

## 9. 実モデル実験の組立案

対象例は「過去の研究ログから出典を回復し、未解決の問いへ次の手順を提案する」仕事とする。これは候補であり、唯一のベンチマークではない。最初に文献と既存実装で答えが出ていないDSCC固有の問いを明記する。

本命は必要な原本、複数候補、検索、批評、失敗記録を利用できる構成にする。比較には強い単独構成、同程度の総費用、引き継ぎ無し、要約のみ、原本付きの構成等を用いる。簡略条件は本命から導き、すべての条件を自然に調整する。

モデル名だけでなく実際のprovider・版・環境、全試行の結果、費用、除外基準を残す。可能なら別課題・別モデルで検証する。閉じたモデルの版が不明なら、その再現上の限界も結果に含める。
