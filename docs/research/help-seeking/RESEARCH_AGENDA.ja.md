## 1. 中心仮説

自分の能力、現在の不足、利用可能な手段、相手の専門性・事情を行動選択へ結び付ける学習を行うと、逐次『ここで相談せよ』と人間が指示しなくても、必要な協力を依頼し、支援後に仕事を継続する方策を育てられる可能性がある。

これは研究仮説である。特に、求助を直接教えた結果と、別の学習目的から副次的に現れた結果は別の主張として評価する。既存研究で答えがある部分は[出典台帳](SOURCES_AND_EVIDENCE.ja.md)から利用し、未解決の接続と汎化へ実験を絞る。

## 2. 八つの研究課題

| ID | 問い | 観測する違い |
|---|---|---|
| R-HS-Q01 | 今の自分だけでは何が足りないかを見分けられるか | 知識・推論・未観測の事実・物理的操作・相手の希望・不明な条件を区別する |
| R-HS-Q02 | 協力の価値とタイミングを選べるか | 追加の自己作業、検索、相談、待機の比較。手遅れになる前の依頼と不要な中断 |
| R-HS-Q03 | 誰に、何を頼むとよいかを見積もれるか | 課題別の専門性、対応可能性、依頼の粒度、必要な資料、応答の見込み |
| R-HS-Q04 | どの教師信号・経験から能力が育つか | 明示的な質問報酬、実演、成果と費用による学習、未直接訓練の副次的能力 |
| R-HS-Q05 | 相手の限界と意思を扱えるか | 拒否、遅延、部分回答、誤回答、相談相手も分からない場合の対応 |
| R-HS-Q06 | 支援を検証して自分の仕事へ戻れるか | 質問しただけ、回答を受けただけ、計画・成果物を実際に修正した場合の違い |
| R-HS-Q07 | 未見条件や自己改良後も判断が合うか | 未見課題・相談相手・道具、モデル更新、以前できたことができない条件 |
| R-HS-Q08 | 長期の相互協力が双方に有用か | 人間の負担、知識移転、反復依頼、参加継続の意思、共同成果と役割変化 |

限界を『自信が低い』一つで表さない。高い自信を持った誤判断も対象にする。また、独力でも解けるが協力すれば費用や時間を大きく減らせる場合があるため、求助を能力不足の証明ができた場合だけに限定しない。

## 3. 本命構成

本命は、観測・検索・実行・批評・相談・共同作業・保留を柔軟に選べるエージェントとする。複数のモデル、原本付き記憶、役割変更、適応的な再質問、独立部分の並行作業を必要に応じて利用する。相談先を唯一の巨大モデルや常時待機する人間に固定しない。

方策が参照する候補情報は、課題と環境の観測、過去の成功・失敗、利用可能な道具、現在の費用、相手が明示した専門性・受付範囲・対応状況である。能力や応答の確かさが未測定ならunknownを許す。相談相手の私的情報や心理状態を推測して依頼を操作する設計にしない。

選択の基準は、共同成果の質、重大な誤りの回避、待ち時間、計算費用、相手の実作業負担を含む。ただし、これらを根拠のない一つの固定重みへ押し込まない。目的・制約を明示し、品質と負担の関係も別々に報告する。

### 不足・相談・許可を別にする

- 不足の申告は、モデルの観測・見積もりであり、必ず正しい診断ではない。
- 協力依頼は相手に選択肢を渡す提案であり、引き受けの強制ではない。
- 回答や協力への同意は、その範囲を超えた資源利用・公開・実行の許可ではない。

知識の質問、現物の観測依頼、物理作業の依頼、判断者本人の希望確認、権限を持つ人への承認要求を同じラベルで採点しない。既存の実行上の承認規則が発火した事例を、モデルの自発的な限界認識の得点に数えない。

## 4. 創発を判定するための学習比較

最初に、基盤モデル、事前学習について分かる範囲、実演、道具説明、報酬、補助損失、外部ゲートを記録する。未学習状態との比較ができない場合は、能力がどこで生じたかを過大に断定しない。

本命では有用な教師信号や記憶を自由に使い、まず強い協働システムを目指す。その後に、目的に対応する比較を派生させる。

| 比較対象 | 答える問い |
|---|---|
| 指示・実演中心 | 行動の形や依頼内容を教えるだけで、何ができるか |
| 明示的な求助の良否を含む学習 | 質問・相談先・タイミングを直接評価すると何が改善するか |
| 成果・費用中心で、求助の正解ラベルを与えない学習 | 選択的な求助がどこまで育つか。探索失敗を含めて測る |
| 他目的で学んだモデルを未訓練の協力課題へ移す | 副次的能力が得られるか。道具利用と人間への依頼を区別する |
| 外部の不確実性ゲート等 | 学習した方策と構成上の規則が、それぞれ何を担うか |

訓練量や調整機会を記録し、比較対象を意図的に弱くしない。役割・層・モデル等を固定する必要がある場合は、その実験内の識別のためか、本命の制約かを明記する。

創発の根拠には、未見課題・相手での行動、学習前後の変化、教師信号の変更に対する変化、複数seedや独立エピソードでの再現を使う。突然の閾値越えだけで判断しない。モデル内部の原因を主張するなら、行動評価とは別に適切な介入実験を必要とする。

## 5. 課題分布と相談相手を混ぜて評価する

| 条件 | 課題例 | 重要な観測 |
|---|---|---|
| 独力で解ける | 必要なログと仕様がすべて手元にある | 不要な丸投げをせず、必要なら費用面で協力を選ぶ |
| 検索で解ける | 許可された原本を調べれば不足を埋められる | 人間に同じ内容を読ませる必要があるか |
| 人間の観測が必要 | 実験ノートの未記録の単位を確認する | 何を確認してほしいか具体的に依頼する |
| 本人の希望が必要 | 成果物の目的や選好に複数の解釈がある | 自信で他者の希望を代用しない |
| 専門的協力が有用 | 別分野の検証や道具の専門家がいる | 誰にどの部分を頼むか |
| 誰も十分には解けない | 原データが失われ、相手も知らない | 回答や完了を捏造せず、不確実さを保つ |
| 相手が拒否・遅延する | 忙しい、範囲外、応答がない | 催促の乱発を避け、別計画・保留・独立作業を選ぶ |
| 相手が誤る | 自信のある誤回答や部分的な助言 | 検証し、根拠を示して確認する |
| 自分の能力が変わる | モデル・道具・利用可能情報を変更する | 古い成功経験を現在の能力と混同しない |

単純な欠落情報だけでなく、誤った高確信、複数の原因候補、途中での条件変更も入れる。相手は完全なoracle、制限された模擬回答者、同意を得た実人間を区別する。理想的な相手も有用な比較だが、その結果を人間との一般的な共生に外挿しない。

最初の実人間試験には低リスクな文献整理、ソフトウェア調査、実験メタデータの確認を候補にする。重大な実機操作で限界認識を試す必要はない。物理的な介入がないテキスト課題でも、情報不足・専門性・負担・再開は調べられる。

## 6. 評価指標

### 適切さと成果

不足検出の精度・見落とし率、相談先の適合、依頼の具体性、重大な誤りの前に頼めた割合、応答後の成果物の品質を分ける。質問した数だけを成功指標にしない。既知の障害数がゼロの課題でrecallを無理に定義せず、不要依頼等を別に評価する。

最終成功率に加え、同じ失敗の反復、誤った確信、未解決なのに完了したという申告、協力が得られなかった場合の挙動を記録する。支援の価値は、独力で失敗したかだけでなく、品質・時間・負担がどう変わったかで判断する。

### 費用と相互性

全役割のモデル利用、検索、通信、待ち時間、再試行、相談相手が読んだ量、実作業時間、中断回数を記録する。未知の費用はゼロとしない。人間の主観的な負担・納得感・継続の意思は、適切な同意の下で別に尋ねる。

人間をすべて同じ能力・負担で扱わず、課題内で必要な専門性や明示された受付条件を利用する。共同成果が高くても一方の負担を極端に増やした構成は、その代償を隠さない。

### 効果と原因

同じ初期条件へ安全に戻せる環境では、支援あり／なし、異なるタイミングや内容の比較ができる。戻せない実人間・外部環境では、観測していない反実仮想を測定値として記録しない。無作為化や対応付けを用いる場合も、人間の学習・疲労・持越しとデータ系列を考慮する。

記録、依頼、受諾、回答、実際の利用、因果的な改善は別の証拠水準である。適切な言い方ができたことから内観の正しさを推定しない。

## 7. DSCCへ残す記録の設計候補

| 残したい情報 | 既存の保存先候補 |
|---|---|
| 能力の不足と未解決点、代替手段 | Hypothesis / OpenQuestion / ResearchState |
| 相談前の状態、依頼内容、参照資料 | 原本ArtifactとAgentContribution |
| 受諾・拒否・遅延・部分回答・取り消し | 原本ArtifactとAgentContributionの履歴 |
| 評価条件、相手とモデルの識別、費用計測 | ExperimentPlan |
| 回答の検証、修正された計画、結果 | EvaluationRun / FailureReport |
| 支援後にどこから続けるか | ResearchState |

最低限、実行・依頼の識別、時点、起点が方策か外部ルールか、何が不足すると見積もったか、実際に送った依頼、相手に見せた原本、応答状態、使った結果、計測費用を結び付ける。要約、自己申告、原観測を混ぜない。hidden chain of thoughtを必要条件にしない。

これらは新しい公開schemaや実装済みの通知サービスではない。既存 `dscc.research/0.1` と [RESEARCH_HANDOFF](../../RESEARCH_HANDOFF.md) を確認し、必要な意味検証は別ADR・adapterで定義する。`content.extensions` にCIDを書くだけでは依存は解決されないため、原本を `input_cids` / `sources` にも明示する。

[PROTOCOL](../../PROTOCOL.md)の小数文字列、記録・親・祖先export上限、大きなblockの別取得を守る。機密の相談内容や評価用の回答を祖先exportで公開しない。公開可能な集計と原本へのアクセス範囲を分け、同じOSユーザーの試作環境を強い隔離と呼ばない。

## 9. 実装経路と研究の順序

**L1 文献と評価契約:** 出典の未読部分を確認し、八つの問いのどこまで既知かを更新する。混合課題、学習信号の開示、支援の種類、評価と負担の記録を決める。

**L2 記録と対話の接続:** T007/T010/T012の既存Artifactへ依頼・応答・再開の履歴を接続する。T001/T002と、実際の送信・同意・停止を行う仕組みを調整する。まず所有者が確認できる小さい協働エピソードで入出力を検証する。

**L3 学習と実モデル評価:** 許可された計算環境で本命構成を訓練・調整し、そこから比較を導く。模擬相手と同意を得た実人間を分け、実人間の特性を模擬結果から決めつけない。

**L4 長期の相互補完:** 新しい参加者やモデルに交代しても、適切な依頼・断り・再開の経験が役立つか検証する。共同成果と負担の両方を継続して測る。

世界規模の分散GPUが完成するまで、文献・記録・小規模評価を止める必要はない。ただし、動いていないモデルや送信機能をmockの成功だけで実装済みにしない。

## 10. 継続調査の更新手順

1. この分野と[出典台帳](SOURCES_AND_EVIDENCE.ja.md)を読み、未解決Q-IDを選ぶ。
2. help-seeking、clarification、learning to defer、metacognitive control、相互補完の一次資料を調べ、既存研究との差を明記する。
3. 各研究に、公開日、確認日、版、読めた範囲、学習信号、回答者、実人間の有無、負の結果、費用、コード・データの利用条件を追記する。
4. 新しい方法を試す前に、文献だけで答えられない問いと強い本命を定める。検証はその問いに対応付ける。
5. 実測を行った場合は、基準commit、構成、データ系列、全試行、未実施のHS-IDを保存する。文書PRだけでは研究Issueを閉じない。

初回の定期調査への登録は所有者の既存DSCC週次調査を利用する。リポジトリに自動連絡・自動訓練・自動マージの機構は追加しない。将来の調査結果を反映するときも、別の変更として差分と根拠を残す。
